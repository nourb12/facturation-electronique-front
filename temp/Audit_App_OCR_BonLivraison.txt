          RÉSUMÉ EXÉCUTIF
            L'application analyse des bons de livraison via OCR et affiche le résultat dans un écran "Modifier le brouillon".
            L'analyse des captures d'écran révèle un score global de 92 % affiché dans l'app, mais la qualité réelle de
            l'extraction est bien inférieure : plusieurs champs sont mal extraits, l'interface est surchargée de blocs
            redondants, des bugs visuels sont présents (overflow), et des champs métier critiques sont totalement absents.
            Ce rapport détaille l'ensemble des défauts et propose des pistes d'amélioration concrètes.

Causes racines des erreurs OCR :
• Confusion de labels : l'OCR détecte le mot-clé de colonne (ex. "Signature", "No") au lieu de la valeur car les
   zones de détection ne sont pas ancrées à la cellule de données.
• Numéro BL mal identifié : "Bon de" est la première occurrence de la ligne du titre — le modèle cherche un
   pattern trop large.
• Tableau d'articles ignoré : la zone structurée (lignes multi-colonnes) n'est pas parsée ; seule la lecture
   linéaire est faite.
• Totaux non reliés : les montants en bas à droite sont extraits isolément sans être associés à leur libellé.
• Absence de post-traitement : aucune validation de format (date DD/MM/YYYY, montant numérique, code
   client alphanumérique) ne filtre les résultats aberrants.


Comment améliorer la qualité OCR :
1. Pré-traitement image : avant l'OCR, appliquer deskew (redressement), débruitage (dénoising),
   rehaussement du contraste et binarisation adaptative (Otsu). Librairies : OpenCV, Pillow.
2. Détection de zones (Layout Detection) : utiliser un modèle de détection de mise en page (ex. DocLayNet,
   PaddleOCR Layout) pour identifier séparément : en-tête fournisseur, bloc client, tableau d'articles, bloc totaux,
   pied de page.
3. OCR orienté tableau : pour la grille d'articles, employer un moteur spécialisé (ex. Table Transformer,
   Camelot, pdfplumber pour les PDF natifs) plutôt qu'un OCR linéaire.
4. Post-traitement & validation : regex pour dates, montants, TVA ; fuzzy-matching pour les noms de
   fournisseurs connus en base ; règle de cohérence : Net HT × (1 + TVA%) = TTC ± Timbre.
5. Feedback loop : quand l'utilisateur corrige un champ dans le brouillon, stocker la paire (extrait → corrigé)
   pour ré-entraîner le modèle de mapping.
6. Résolution minimale : exiger 300 DPI pour les scans ; afficher un avertissement si la photo est floue (score
   de netteté Laplacian < seuil).
7. Modèle LLM multimodal : envisager d'utiliser un modèle vision (ex. Claude, GPT-4o) pour interpréter
   directement le document et retourner un JSON structuré — beaucoup plus robuste que l'OCR classique pour
   les documents non standardisés.

3. RECOMMANDATIONS UX/UI — REFONTE DE L'ÉCRAN
 Architecture d'écran recommandée (écran unique, scrollable) :
ZONE 1 — En-tête sticky
  • Titre : 'Bon de livraison N° 202501069' (numéro extrait dynamiquement)
  • Badge score de confiance global (recalculé) + icône de statut
  • Bouton 'Voir le document' → modal plein écran avec zoom

ZONE 2 — Classification (NOUVEAU)
  • Toggle 'Type' : [ Achat | Vente ] avec style pill sélectionnable
  • Toggle 'Statut paiement' : [ Payé ■ | En attente ■ | Impayé ■ ]
  • Ces deux choix orientent le routage vers le bon module du dashboard web

ZONE 3 — Champs détectés (fusionnés, un seul bloc)
  • Chaque champ sur une ligne : Libellé — Valeur — Badge (Fiable/À vérifier/Absent)
  • Les champs modifiables ont un fond éditable (tap → keyboard)
  • Section 'Fournisseur' intégrée ici : plus de bloc séparé
  • Section 'Client' intégrée ici : symétrique au fournisseur
  • Ordre logique : Info BL → Fournisseur → Client → Articles → Totaux → Paiement

ZONE 4 — Lignes d'articles (NOUVEAU)
  • Tableau scrollable horizontal : Réf | Désignation | Qté | PU HT | Remise | TVA | Total HT
  • Chaque ligne est éditable individuellement
  • Bouton '+' pour ajouter une ligne manquante

ZONE 5 — Totaux (NOUVEAU)
  • Affichage structuré : Brut HT / Remise / Net HT / TVA / Timbre / Total TTC
  • Validation automatique : si Net HT × 1.19 ≠ Total TTC → warning orange

ZONE 6 — Barre d'actions (sticky bottom)
  • Bouton secondaire : 'Enregistrer le brouillon'
  • Bouton primaire : 'Valider et envoyer' (désactivé tant que champs obligatoires vides)
  • Supprimer le texte 'OVERFLOWED BY 23 PIXELS' — aucune raison d'être en prod

6. CONCLUSION
 L'application présente une bonne idée de base — scanner et analyser automatiquement les bons de livraison —
 mais souffre de défauts bloquants à la fois sur la qualité OCR, l'interface utilisateur et la couverture métier. Le
 score affiché de 92 % est trompeur : en pratique, les deux champs les plus critiques (numéro BL et fournisseur)
 sont incorrects, et la moitié des champs comptables sont absents.

 La priorité absolue est de corriger les mappings OCR, supprimer les artefacts de debug, et refondre
 l'architecture de l'écran en un seul bloc cohérent. L'ajout du module de classification (achat/vente, statut
 paiement) et des champs manquants transformera l'outil en un vrai assistant comptable mobile.

 À terme, le passage à un modèle vision multimodal pour l'extraction est fortement recommandé : il éliminera la
 majorité des erreurs OCR structurelles et s'adaptera naturellement aux variations de mise en page entre
 fournisseurs.
